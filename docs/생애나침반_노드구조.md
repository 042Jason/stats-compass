# 생애나침반 노드 구조

데모(`docs/생애나침반_페르소나데모.html`)의 흐름을 실제로 돌리려면 무엇이 있어야 하는지 정리한 문서입니다.
현재 구축된 것과 아직 없는 것을 구분했습니다.

---

## 0. 먼저 짚을 것 — 노드가 아닌 것

데모 그림에서 노드처럼 보이지만 **온톨로지 노드가 아닌** 층이 둘 있습니다. 헷갈리면 설계가 어긋납니다.

| 그림의 층 | 실제 정체 | 사는 곳 |
|---|---|---|
| **입력 조각** ("35살", "월급 얼마") | 질의를 쪼갠 문자열. 저장하지 않습니다 | 요청 처리 중 메모리 |
| **별칭** ("월급 얼마", "빚") | 노드의 `alt_labels` 원소이자 **임베딩 행 1건** | `ontology_entities.alt_labels` + `ontology_embeddings(kind='alias')` |
| **규칙** (나이 → 생애단계) | 코드 안의 매핑 함수 | `src/utils/lifestage.ts` (미작성) |

별칭을 노드로 만들면 안 됩니다. 별칭은 1,143개인데 노드화하면 그래프가 별칭으로 뒤덮이고,
`skos:altLabel` 의 의미(같은 것을 가리키는 다른 이름)와도 어긋납니다.
대신 **별칭마다 벡터를 따로 두어** 검색에서만 독립적으로 걸리게 합니다.

## 3. 검색 파이프라인에서 각 층이 하는 일

데모의 일곱 단계를 실제 구현으로 옮기면 이렇습니다.

```
질의 "대전 사는 35살 남잔데, 또래들 월급 얼마나 받는지, 집 살 때 빚은 얼마나 지는지"
  │
  ├─① 슬롯 추출  ────────────────────────────────  lifecourse_parse
  │     정규식 + LLM. 나이 35 / 성별 M / 지역 "대전"
  │     ↳ 지역명은 Region 노드 라벨·별칭과 사전 매칭 → 코드 30
  │     ↳ 나이는 AgeBand("30~39세") → stageForAge → LifeStage 3개
  │
  ├─② 별칭 매칭  ────────────────────────────────  graphrag_search
  │     ontology_embeddings 를 두 갈래로 조회
  │       · 어휘: similarity(content, 질의) — "월급 얼마" "빚" 이 여기서 걸림
  │       · 벡터: embedding <=> 질의벡터   — 문장 전체 의미가 여기서 걸림
  │     RRF 로 순위 합산 → 노드당 최고 청크 하나만 남김
  │
  ├─③ 진입 노드  ────────────────────────────────
  │     별칭이 가리킨 Indicator + 규칙이 정한 LifeStage
  │
  ├─④ 후보 확산  ────────────────────────────────  1홉
  │     Indicator ─measuredBy→ Survey
  │     LifeStage ←coversLifeStage─ Survey
  │
  ├─⑤ 통계용어  ─────────────────────────────────
  │     Survey ─definesConcept→ Concept
  │     같은 Concept 을 무는 Survey 끼리가 곧 다리
  │
  ├─⑥ 가지치기  ─────────────────────────────────
  │     · oftenConfusedWith 가 걸린 쌍 → 하나만 남김
  │     · regionLevel = '전국만' 인데 지역 슬롯이 있으면 → 경고 플래그
  │     · 같은 Concept 을 공유하고 점수가 낮으면 → 중복 제외
  │
  └─⑦ 통계표  ───────────────────────────────────
        Survey ─hasDistribution→ StatisticalTable
        availableFor(Region) · hasAgeBand · hasSexDim 로 최종 필터
        → orgId / tblId 를 KOSIS API 로 넘김
```

## 4. 임베딩 레이어

`ontology_embeddings` 는 노드와 **1:N** 입니다. 한 노드가 여러 벡터를 가집니다.

| kind | 내용 | 예상 건수 | 왜 나누는가 |
|---|---|---|---|
| `main` | 라벨 + 정제 개요 | ~2,000 | 노드 자체의 의미 |
| `alias` | 별칭 하나당 한 행 | **1,143** | 짧은 별칭을 본문에 섞으면 벡터가 흐려짐 |
| `meta` | KOSIS 설명자료를 항목별로 자른 청크 | ~400 | 조사목적·조사대상·**조사항목**·주요용어·유의사항·연혁 |

합계 약 3,500행. `text-embedding-3-small` 기준 비용은 몇 센트입니다.

**어휘 검색(`pg_trgm`)이 왜 필요한가** — "빚" 두 글자를 문장 전체 벡터와 비교하면 유사도가 0.2대입니다.
벡터만 쓰면 짧고 정확한 별칭을 놓칩니다. 반대로 어휘만 쓰면 "또래들은 어떻게 사는지" 같은 표현을 못 잡습니다.
둘을 RRF 로 합쳐야 양쪽이 다 걸립니다.

## 5. 지금 없는 것을 만드는 법

### 5-1. Region (우선순위 1)

KOSIS 지역코드는 시도 2자리, 시군구 5자리입니다.

```
Region 노드
  key    = "30"            (KOSIS objL 코드)
  label  = "대전광역시"
  alt    = ["대전", "대전시"]
  props  = { level: "시도", parent: null }
```

- 시도 17개는 고정 목록으로 바로 만들 수 있습니다.
- 시군구 229개는 통계표 분류값에서 뽑거나 행정표준코드로 채웁니다.
- `availableFor` 는 1차로 **통계표명 정규식**(`시도|시군구|지역별`)으로 근사하고,
  정확도가 필요하면 KOSIS `statisticsData.do` 의 분류 메타를 추가 수집합니다.

### 5-2. AgeBand · Sex (우선순위 2)

```
AgeBand: 0~9세 / 10~19세 / … / 80세이상, 그리고 "15~64세" 같은 집계 구간
Sex:     남자 / 여자 / 계
stageForAge: 30~39세 → 취업·일자리, 결혼·가구형성, 주거·자산
```

`stageForAge` 를 데이터로 두면 **나이 → 생애단계 규칙이 코드에서 그래프로 옮겨집니다.**
지금은 하드코딩이라 바꾸려면 배포해야 합니다.

### 5-3. Dimension (우선순위 3, 확장)

KOSIS 통계표마다 분류축(`objL1`~`objL8`)과 항목(`itmId`)이 있습니다.
이걸 수집하면 `qb:DimensionProperty` 로 세워 **"어느 표의 어느 셀"** 까지 답할 수 있습니다.
다만 통계표 1,386개 × 분류 메타 호출이라 KOSIS 호출제한(분당 200)을 고려하면 7분 이상 걸립니다.
POC 범위 밖으로 두었습니다.
